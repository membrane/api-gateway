## Security

- `javascript`: every execution only sees the values of its own exchange. Before, a script could see the `json` body, `param`/`params` and `response`/`statusCode` of an earlier exchange, and top-level variables such as `var user` set by an earlier request. With GraalVM this also applied to scripts of other APIs, with Rhino also to changes to built-in objects such as `Object.prototype` [#3631](https://github.com/membrane/api-gateway/pull/3631)
- `template`: in production mode, the error response no longer contains the line number, the surrounding template lines or the name of a missing property or method. They are logged under the log key the response shows [#3683](https://github.com/membrane/api-gateway/pull/3683)
- `template` and `soapBody` with XML: values that are not a string or an XML node, e.g. a JSON array or a Groovy string built with `"${...}"`, are XML-escaped too [#3682](https://github.com/membrane/api-gateway/pull/3682)
- `soapBody`: values inserted with `${...}` are always XML-escaped, whatever `contentType` is set to. Before, a value such as a query parameter could add elements to the SOAP message. XML markup inserted from a string is now escaped as well [#3682](https://github.com/membrane/api-gateway/pull/3682)

## Fixes

### OpenAPI
- `multipart/form-data` and form validation:
  - `$ref` request body schemas are resolved, also with OpenAPI 3.1 constraints next to the `$ref`
  - A missing component is reported as an `openapi-parsing` error
  - Inline `additionalProperties` is applied

  [#3663](https://github.com/membrane/api-gateway/pull/3663)
- `minimum`, `maximum`, `exclusiveMinimum`/`exclusiveMaximum` and `multipleOf`:
  - They are checked with exact precision, also for path parameters, form fields, multipart parts and XML values
  - They apply only to numbers, as in JSON Schema. Declare `type: integer` or `type: number` for untyped parameters
  - `multipleOf` handles large exponents such as `1e10000000` without excessive CPU and memory use

  [#3663](https://github.com/membrane/api-gateway/pull/3663)
- An invalid `patternProperties` regex is reported as an `openapi-parsing` error (`500`) instead of a `400` [#3663](https://github.com/membrane/api-gateway/pull/3663)

## Breaking Changes

### JSON and OpenAPI Validation
- JSON bodies with data after the first value, e.g. `{"a":1}{"b":2}` or NDJSON, are now rejected by `validator`, `openapi` and `jsonRPCProtection` [#3663](https://github.com/membrane/api-gateway/pull/3663)
- JSON Schema `validator`:
  - Bodies are read as UTF-8/16/32 as RFC 8259 requires, and the `charset` parameter is ignored [#3663](https://github.com/membrane/api-gateway/pull/3663)
  - Errors no longer contain `node`; use `pointer` instead. At most 10 errors are reported, plus `"errorsTruncated": true` if there are more
- OpenAPI `multipart/form-data`: a part whose Content-Type is a media range (`application/*`) is rejected. So is an object or array part with a Content-Type other than JSON or XML, unless its `encoding` declares that type. A malformed part Content-Type now gives a validation error instead of a `500` [#3663](https://github.com/membrane/api-gateway/pull/3663)
- OpenAPI XML: with `additionalProperties: false`, attributes and child elements that no property maps to are now rejected instead of silently dropped [#3663](https://github.com/membrane/api-gateway/pull/3663)

### Plugins
- `javascript` [#3631](https://github.com/membrane/api-gateway/pull/3631):
  - GraalVM: each execution runs in its own context. Objects created by the script can't be used after it finishes, so store them with `JSON.stringify(...)`
  - Rhino: whole numbers are passed to Java as floating point (`{"id":7.0}`), and a syntax error now stops startup
  - A script that ends with an array sets the body to that array as JSON
  - `rhino-engine` (JSR 223) is no longer bundled. Add it to `lib` if custom code uses `getEngineByName("rhino")`
- `clusterNotification`: `/clustermanager/up`, `/down` and `/takeout` accept only POST and answer `405` otherwise. `down` and `takeout` answer `404` for unknown nodes. See the migration guide [#3672](https://github.com/membrane/api-gateway/pull/3672)
- `cors`: setting `allowAll` together with `credentials`, or giving an invalid origin, is now a configuration error at startup [#3641](https://github.com/membrane/api-gateway/pull/3641)
- `llmGateway`: when policies or a user store are configured, requests the restrictions cannot be applied to are rejected with `400`. Examples are other endpoints such as `/v1/embeddings` or `/v1/messages/count_tokens` [#3675](https://github.com/membrane/api-gateway/pull/3675)
