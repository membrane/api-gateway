- Bodies with `Content-Encoding: zstd` (RFC 9659) can now be decoded like gzip, deflate and br, so plugins that read the body, such as validators, `template`, JSONPath/XPath expressions and scripts, get the content instead of the compressed bytes, and `limit` counts the decoded bytes. Decoding is off by default and is switched on with the system property `-Dmembrane.core.http.zstd.decode=true` (e.g. in `JAVA_OPTS`). While it is off, zstd is handled like any coding Membrane does not decode: bodies are forwarded unchanged, and the first zstd body that a plugin or `limit` reads logs a warning that explains how to switch decoding on or how to keep backends from answering with zstd by removing it from `Accept-Encoding`. It is off because the decoder (aircompressor) accesses memory through `sun.misc.Unsafe`, without the bounds checks of the JVM, so a bug in it could crash the JVM or expose memory, as CVE-2024-36114 did in aircompressor before 0.27; Membrane ships the latest aircompressor 2.x release. With decoding switched on, from JDK 24 on, the JVM prints a deprecation warning on stderr when it decodes the first zstd body, and a JVM that denies this access, as `--sun-misc-unsafe-memory-access=deny` does and later JDKs are to do by default, cannot decode zstd: Membrane then logs an error once and forwards zstd bodies unchanged. A zstd frame that needs a window larger than 8 MB is rejected, following the limit RFC 9659 sets for this coding, with 400 for a request and 500 for a response if this happens before the message is forwarded. [#3785](https://github.com/membrane/api-gateway/issues/3785)
