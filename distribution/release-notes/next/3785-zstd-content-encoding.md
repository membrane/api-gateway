- Bodies with `Content-Encoding: zstd` (RFC 9659) are now decoded like gzip, deflate and br, so plugins that read the body, such as validators, `template`, JSONPath/XPath expressions and scripts, get the content instead of the compressed bytes, and `limit` counts the decoded bytes. Browsers offer zstd in `Accept-Encoding`, so backends increasingly answer with it. A zstd frame that needs a window larger than 8 MB is rejected, following the limit RFC 9659 sets for this coding, with 400 for a request and 500 for a response if this happens before the message is forwarded. The zstd decoder (aircompressor) uses `sun.misc.Unsafe`: from JDK 24 on, the JVM prints a deprecation warning on stderr when it decodes the first zstd body. A JVM that denies this access, as `--sun-misc-unsafe-memory-access=deny` does and later JDKs are to do by default, cannot decode zstd: Membrane then logs an error once and handles zstd like a coding it does not decode, so such bodies are forwarded unchanged. The zstd decoder accesses memory without bounds checks, so a bug in it could crash the JVM or expose memory, as CVE-2024-36114 did in aircompressor before 0.27. It only runs when a plugin reads a zstd body, and `limit` does so for every zstd body it forwards; Membrane ships the latest aircompressor 2.x release [#3785](https://github.com/membrane/api-gateway/issues/3785)
