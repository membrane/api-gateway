# 7.9.0

## Breaking Changes

- JSON bodies with data after the first JSON value, e.g. `{"a":1}{"b":2}` or `{"a":1} xyz`, are now rejected by the JSON Schema `validator`, `openapi` validation and `jsonRPCProtection`. Before, only the first value was validated while the whole body was forwarded to the backend. Clients that send several JSON values in one body, e.g. JSON Lines/NDJSON, to a validated API now get an error.
- OpenAPI `multipart/form-data` validation: a part with a media range as Content-Type, e.g. `application/*`, is rejected. Before, it matched a declared `encoding` like `application/json` and its content was not validated. An object or array part sent with a Content-Type other than JSON or XML, e.g. `text/plain` or `application/octet-stream`, is now rejected unless the `encoding` of the part declares that Content-Type. Before, such a part was accepted without validation against its schema.
- A multipart part with a malformed Content-Type now receives a validation error instead of causing an internal server error.
- OpenAPI XML validation: an XML body or `multipart/form-data` XML part is rejected if an object with `additionalProperties: false` contains an attribute or child element that no property is mapped to. Before, such content was dropped while converting the XML for validation, so the body passed and was forwarded to the backend with it. Namespace declarations, `xsi:` and `xml:` attributes, e.g. `xml:lang`, and names matching `patternProperties` are still allowed.
- JSON Schema `validator`: JSON bodies are read as UTF-8 (or UTF-16/32, detected from the content) as required by RFC 8259, and the `charset` parameter of the Content-Type is ignored, as in `openapi` validation. Before, a body sent with e.g. `charset=ISO-8859-1` was decoded with that charset; if it contains non-ASCII characters, it is now rejected as invalid JSON.
- JSON Schema `validator`: errors no longer contain `node`, the validated value. Each `additionalProperties` error carried the whole object, so the error response grew with the number of forbidden properties times the size of the body. Use `pointer` to locate the error. At most 10 errors are reported; if there are more, the response contains `"errorsTruncated": true`.

### Plugins
- `javascript` with GraalVM: every execution of the script now runs in its own JavaScript context, which is closed afterwards. Objects created by the script, such as `{a: 1}` or the result of `JSON.parse()`, can no longer be used after the script has finished: storing one on the exchange, e.g. with `property.put('order', order)`, and reading it later in another plugin fails with `The Context is already closed`. Store it as a string instead: `property.put('order', JSON.stringify(order))`. Strings, numbers and Java objects such as `json`, `header` or `message` are not affected. An execution also takes longer than before, about 0.1 ms instead of 0.015 ms [#3625](https://github.com/membrane/api-gateway/issues/3625)
- The distribution no longer contains `rhino-engine`, the JSR 223 script engine of Rhino. Rhino itself is still included and used by the `javascript` plugin. Only custom code that gets Rhino through `javax.script`, e.g. with `getEngineByName("rhino")`, is affected; add `rhino-engine` to `lib` for it [#3625](https://github.com/membrane/api-gateway/issues/3625)
- `javascript` with Rhino: whole numbers written or computed in the script are now passed to Java as floating point numbers. A script that ends with `({id: 7})` now sets the body to `{"id":7.0}` instead of `{"id":7}`, and `property.put('count', 3)` stores `3.0`. Values taken from `json` or from Java objects keep their type: `({id: json.id})` still sets `{"id":7}`. Inside the script nothing changes, and a number converted to a string, e.g. with `'' + 7`, is still `7`. Rhino now interprets the script instead of compiling it to Java bytecode [#3625](https://github.com/membrane/api-gateway/issues/3625)
- `javascript`: a script that ends with an array, e.g. `[1, 2]` or `items.map(...)`, now sets the message body to that array as JSON, like a script that ends with an object. Before, the array was ignored with Rhino and set the body to `{}` with GraalVM. End such a script with `CONTINUE` to leave the message unchanged [#3625](https://github.com/membrane/api-gateway/issues/3625)
- `javascript` with Rhino: a script with a syntax error now stops Membrane from starting, like other configuration errors. Before, Membrane started and every execution of the script failed with a 500 [#3625](https://github.com/membrane/api-gateway/issues/3625)
- `clusterNotification`: `/clustermanager/up`, `/down` and `/takeout` accept only POST, like the actions of the admin console that change the state of a load balancer. Other methods are answered with `405`. Scripts that call the cluster manager with GET have to use POST, e.g. `curl -X POST "localhost:9000/clustermanager/up?host=node1.example.com&port=8080"`. `down` and `takeout` answer `404` for a node that is not registered instead of registering it; use `up` to register a node. See the migration guide [#3672](https://github.com/membrane/api-gateway/pull/3672)

## Improvements

### Plugins
- `javascript` with Rhino: an execution of the script takes about 0.1 ms instead of 0.28 ms [#3625](https://github.com/membrane/api-gateway/issues/3625)

### XML
- XML nested deeper than 100 levels is no longer rejected as not well-formed when Membrane parses SOAP and other XML messages, e.g. to find the SOAP operation, rewrite a WSDL or beautify XML. Since JDK 24, the JDK limits the depth to 100 by default (`jdk.xml.maxElementDepth`); Membrane now lifts this limit, as it does not decide how deep the documents of an API may be (ADR-007). To limit the depth, use `xmlProtection` with `maxDepth`, or `limit` with `maxBodyLength`

## Fixes

### OpenAPI
- `multipart/form-data` validation: a request body schema that is a `$ref` to a component, e.g. `$ref: '#/components/schemas/Upload'`, is now resolved. Before, the component's required parts, property schemas and `additionalProperties: false` were ignored, and every multipart body passed.
- `multipart/form-data` and `application/x-www-form-urlencoded` validation now also apply OpenAPI 3.1 constraints alongside a root `$ref`, including required parts and fields, property schemas and `additionalProperties`. Previously only the referenced component was checked.
- `multipart/form-data` and `application/x-www-form-urlencoded` validation: a request body schema that is a `$ref` to a missing component, e.g. `$ref: '#/components/schemas/Missing'`, is now reported as an error in the OpenAPI document: the request fails with a 500 of type `openapi-parsing`. Before, every body passed without validation.
- `multipart/form-data` and `application/x-www-form-urlencoded` validation: `additionalProperties: false` in an OpenAPI 3.1 schema inline at the media type now rejects undeclared fields. If `additionalProperties` is a schema, undeclared fields are now validated against it. Before, both were accepted unchecked.
- Path parameters: `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum` and `multipleOf` are now checked with exact precision. Before, the value was converted to a double: values beyond its range, e.g. `-` followed by 309 nines, skipped all of these checks, and values close to a limit, e.g. `5.0000000000000000001` against `maximum: 5`, were rounded and accepted.
- Form fields, `multipart/form-data` parts and XML values: numbers are now also checked with exact precision. Before, `5.0000000000000000001` was accepted by `maximum: 5`, `1e400` was reported as not a number, and an integer with more than 19 digits was reported as not an integer instead of being checked against `minimum` and `maximum`. Java notations such as `1d`, `0x1p3`, `NaN` or `Infinity` are no longer accepted as numbers. A number with more than 1000 characters, the limit that also applies to numbers in JSON bodies, is rejected with an error that names its length.
- Numeric `multipleOf` validation handles large exponents without expanding them into huge integers, preventing excessive CPU and memory use or arithmetic errors for compact values such as `1e10000000`.
- `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum` and `multipleOf` now apply only to numbers, as in JSON Schema. Before, a string of digits, e.g. `"7"` against `maximum: 5`, was also compared with them, and every validated string was parsed as a number, which took excessive CPU time for long strings. Query parameters, form fields and XML values whose schema has no `type` are strings, so these keywords no longer apply to them; declare `type: integer` or `type: number`.
- An invalid regular expression in `patternProperties`, e.g. `"["`, is now reported as an error in the OpenAPI document: the request fails with a 500 of type `openapi-parsing`, and the log names the regex. This applies to JSON, XML, `multipart/form-data` and `application/x-www-form-urlencoded` bodies and to exploded object query parameters. Before, JSON bodies, JSON multipart parts and query parameters were rejected with a 400 as if the client had sent invalid data, and XML bodies failed with a generic 500.

### Plugins
- `groovy` and `javascript` in an `abort` block now run when the exchange has no response yet, e.g. because a script in the request flow returned `ABORT`. Before, the script did not run, and the client got a 500 `Error executing script.` with a `NullPointerException`. Without a response, `response`, `statusCode`, `message`, `body`, `header`, `headers`, `cookie`, `cookies` and `json` are `null`, and the script can create the response itself, e.g. by returning a `Response` [#3635](https://github.com/membrane/api-gateway/issues/3635)
- `javascript` with GraalVM: a script whose last statement has no value, such as `var x = 1;`, no longer replaces the message body with `null`. A script that ends with a string now sets the body to that string, and a script that ends with a number leaves the message unchanged, as with Rhino. Before, a string or a number failed with a `ClassCastException`, and an array set the body to `{}` [#3625](https://github.com/membrane/api-gateway/issues/3625)
- `javascript` with Rhino: `console.log()` now prints all its arguments instead of only the first one, and Javascript objects and arrays as JSON instead of `[object Object]`. `print()` separates its arguments with spaces, as with GraalVM. `console.log('id', 7)` printed `id` and now prints `id 7` [#3625](https://github.com/membrane/api-gateway/issues/3625)
- `javascript` with Rhino: a variable that is declared but not assigned, such as `json` for a message that is not JSON, is now `undefined`. Before, it was the string `"undefined"`, so `if (json)` was true for every message [#3625](https://github.com/membrane/api-gateway/issues/3625)

## Security
- `javascript`: a script could see the values of an earlier request: the `json` body of an earlier request when the current one is not JSON, `param`/`params` and `response`/`statusCode` of an earlier exchange, and its own top-level variables, such as `var user`, set by an earlier request. With GraalVM, this also applied to scripts of other APIs. With Rhino, changes to built-in objects, such as a property added to `Object.prototype`, were also visible to later executions. Every execution now only sees the values of its own exchange [#3625](https://github.com/membrane/api-gateway/issues/3625)
